# Connectors and their hosts

Each source is an island package in [elt](https://github.com/ezzabuzaid/elt), for example `packages/sources/apple/<name>` (`source-apple-<name>`) with its readers and tests; the readers several sources share are in `source-apple-macos`, and EventKit access with its Swift helper in `sdk-apple-eventkit`. See elt's [reference](https://github.com/ezzabuzaid/elt/blob/main/docs/reference.md) for each source's streams.

## Connector packages

The connectors live in `packages/connectors`, one package each, named after the source package it imports (`source-apple-mail` → `connector-apple-mail`, `source-slack-desktop` → `connector-slack-desktop`). Its `package.json` is the manifest: `"type": "module"`, an `exports` string naming the entry point, and a `contextCompiler` field with the connector's `name` and `title`. The entry's default export is the connector's `Connector` class (`connector`), which takes its name and title from the manifest and declares what the connector can be narrowed by, its permission guidance and how it loads.

`Connectors` in `connector-manifest` reads the folders under the roots a host gives it, in name order, skips any whose `package.json` declares no connector, loads each entry and creates its connector with the host's `ConnectorHost`, which names the app macOS grants access to and may offer a Google session; a connector that cannot be read or loaded is reported with its error while the others load. Both hosts load their connectors that way: the CLI from `packages/connectors`, whose packages it depends on, the plugin from the connector folders bundled beside its server, and both then from the user's own folder, `~/Library/Application Support/Context Compiler/Connectors`, where a connector is added without a release.

A user's connector is TypeScript that Node runs as written: its entry is a `.ts` file, named by a `package.json` beside it, using only syntax Node can strip (no enums or parameter properties), and every stream and field it declares carries a JSON Schema `description` for its reader view. It imports `@workspace/elt`, `@workspace/connector/connector` and `@workspace/connector/choice` from its host, as the built-in connectors do: `provideHostModules` registers a resolve hook that maps those specifiers to the host's own copies (the CLI's workspace modules; the plugin's `server/modules`, which re-export its shared chunks), so its classes pass the host's checks.

The plugin adds the connectors that could not load to every chat's status; the CLI writes them to stderr. The plugin discovers its connectors again before every tool call and import pass, so a connector added or edited while a chat is open is used without a restart; an edited entry loads again because its import URL carries the file's modification time, while files it imports load once. Because Codex keeps a chat's tool list as it began, `options` and `configure` take the connector as a string checked when they run, not an enum. A selected connector that is not loaded is reported, not thrown on: its status says how to restore or disconnect it, the plugin keeps its selection unchanged through other changes (and refuses to change it), and the CLI's `sync` records the failure and still loads the other connectors. `$add-connector` is the plugin skill that tells the agent how to write one.

## The hosts

The CLI imports directly; the Codex plugin and desktop app use the same MCP server:

- `apps/cli` (`npx nx run cli:start -- <command>`) shares `~/Library/Application Support/Context Compiler/Imports` with the plugin and desktop by default; `--directory <path>` selects a separate store. `sync` runs one pass of each selected connector. `sync watch` keeps them current: it runs a pass at once, then one for each change each source reports, until Ctrl-C or SIGTERM stops it. Its Calendar import signs in to Google for Drive and Gmail attachments, so `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET` must be set.
- `apps/server`, shared by the Codex plugin and Electron desktop, bundled for the plugin by `npx nx run plugin:bundle` into `plugins/context-compiler/server` (`main.mjs`, a folder per built-in connector beside it, and the chunks they share, so every connector runs on the server's own `elt` and `Connector`; build output, ignored on main and published with the plugin to the `release` branch Codex installs from), is the Codex plugin's MCP server: a server imports a connector when the user connects it or changes what it imports, every connected connector again when the user presses Sync on the Context Compiler page, and one connector when the user picks Sync in its row's right-click menu (`sync`, whose optional `connector` names it). A connector the user keeps current (`connector_watch`) also loads each change while any of its servers runs: each server stands by for the import's owner claim (the CLI's `SqliteElection`), the owner watches it, a server whose chat closed or whose plugin was updated gives it up, and Sync of it runs no pass of its own. Nothing else refreshes or retries an import on its own. The plugin's hooks call its `context` tool to give each chat the status when the chat starts and whenever it changes. Codex keeps an older chat's server running after an upgrade but deletes that version's folder, so that server stops importing and tells the chat to open a new one. Its Calendar keeps remote attachments as links.

Each import holds one `data.sqlite` with `raw_<stream>` tables read through `<snake_stream>` views, its sync history and `catalog` views, `checkpoints.sqlite`, and a `files` folder. Each host records every pass and its declared extraction coverage with `SQLiteSyncHistory` in the import's own `data.sqlite`.

No version number marks these files. Each owner compares the tables it keeps with their CREATE statements through a `Declaration` (`@zukhruf/sqlite-drift`), and replaces a table that another version declared otherwise, with its rows. The sync history is replaced when the next pass installs it, and until then `readPassStatus` reads it as no status. `checkpoints` is replaced when a pass opens it, and each copy starts over. The settings tables are replaced when `Settings` opens them, and the user sets up again. Each selection's folder comes from its scope and attachment choice (`importDirectory`).

## Imports and their owners

Both hosts keep their selection in `settings.sqlite` through `Settings` (`@workspace/settings`) and run each import the same way, through `Connector.import(settings, selection, history)`, inside the import's flight: a `SingleFlight` (`@zukhruf/single-flight`) whose processes meet in the host's root folder and whose key is the import's folder. The first process to ask runs the pass; one that asks while it runs joins it and gets its outcome instead of running another. The CLI's `sync` shows the joined pass's lines, or reports the import as interrupted and exits 1 when the sync running it is killed; the plugin's servers wait silently. Status comes from `readPassStatus()` (`elt-sqlite`), which reports the sync history as it is, so a pass a killed process left reads `running` until the next pass.

Removing a connector, from the CLI's `setup`, another chat or the Context Compiler page, saves the selection first, so readers stop seeing it at once. Removing stale imports is reconciliation at safe points: a selection change and the start of a CLI `sync` remove each folder `Settings.staleImports()` lists by leading that import's flight, and skip one whose pass is in flight, since a pass keeps its locks inside the folder. In the CLI a later safe point removes it; in the plugin that pass removes its own folder when it ends. The pass checks the selection about once a second, through `PRAGMA data_version` on `settings.sqlite`, and stops at its next message once its connector is gone; the CLI reports it as removed without failing the sync.

The CLI also elects one owner for each import with `SqliteElection` (`@zukhruf/election`). A `sync` holds the claim for its pass, and a `sync watch` holds it until it stops. The claim file, `<connector>.<selection>.owner.lock`, is in the root folder, so the removal of an import's folder never deletes a claim that a waiting watch keeps open. A `sync` that cannot win the claim runs no pass and reports the import as `watched`. A `sync watch` that cannot win it reports `waiting`, and owns the import when the owner stops or dies: the kernel frees the claim with the owner's process. A stale import whose claim is held is not removed; its watch hears of the removal within a second and stops, and the next safe point removes the folder. An import whose source stops reporting changes, such as a connector whose `observe()` ends, stops alone and reports `stopped`; the other imports keep watching.

One-shot imports use `p-retry` only for errors the connector's `retryImport` identifies. Mail identifies `MailChangingError`: at most two retries, after 250 and 500 ms, each opening a fresh source snapshot and resuming committed checkpoints. Every attempt records its own sync history; a persistent failure stays partial or failed. An unrelated failure does not prevent retrying a concurrent file change, and remains reported afterwards. Permission and schema errors alone are not retried. Cancellation stops extraction and backoff; a stop after a pass committed preserves that successful outcome and stops attachment parsing.

## Presets and views

A connector's presets are SQL files in a `presets` folder beside its manifest, built-in or the user's alike. `presets/<view>.sql` holds one `CREATE TEMP VIEW <view>` over the connector's views, after `-- <view>: …` and `-- <column>: …` comment lines that describe the view and each column in order; Mail's `mail_messages` is one row per message with its sender, recipients, subject, Message-ID, body and attachments. A preset is the source's data in a shape readers ask for, not the answer to one question, and nothing stores it: a reader loads it for one connection, so the import is unchanged and `catalog` does not list it. `Connector.presets()` lists the folder whenever it is asked, so a preset added to a user's connector is offered without a restart. The plugin's bundle copies each built-in connector's `presets` beside its entry; the status names the folder and its presets under each loaded connector, and the query skill loads one with `sqlite3 -readonly -cmd '.read "<file>"'`. The CLI's `query` loads every preset of the connector before the statement, and `--tables` lists them. `mail_messages` leaves out `attachmentRef`, which exists only when an import copies attachments; it is read from `attachments` on `messageId` and `partId`. See [subscription presets](subscription-presets.md) for presets that span connectors.

A connector can also publish views in its import. `Connector.views(copied)` returns `SQLiteView`s over the connector's own views; the connector publishes them, with their descriptions in `catalog`, after each pass. While a stream the import copies has not loaded yet, a view that reads it waits and the others are published; once every stream loaded, a view that cannot be published fails the import. `copied` names the streams the import holds, fewer in a narrowed import, so a view reads only those. Mail publishes `mail_content_status` this way.

Mail's `mail_messages` preset exposes both `body_text` and `body_html`; a plain-text alternative can omit details present in HTML, so readers inspect both. `body` remains a convenience fallback. Subscription evidence searches both representations and retains differing HTML with the matched text. Mail also publishes `mail_content_status`: the newest locally received message date, message count, messages without a downloaded file or readable body text, attachment count and attachments unavailable on this Mac, limited to the imported selection. The Context Compiler page and chat show these facts alongside the import's `current_as_of`, explicitly distinguishing local availability from unknown cloud inbox freshness. A message without readable text can be downloaded but encrypted or have no text part. Partial passes can leave content streams from different reads; `stream_status` identifies them. Let Mail update its accounts to obtain newer messages and missing content; the import itself reads the local store.

## Attachment text

The text of each file that an import stored goes into the `data.sqlite` of that import. Readers use SQL to search the attachments. The `attachment_text` view holds one row for each stored copy. These are its columns:

- `ref`: the path of the stored copy, relative to the `files` folder of the import. The `attachmentRef` column of each row that holds the file has the same value. The file name of the copy is the SHA-256 of its bytes.
- `input_hash`: the SHA-256 of the input that made the row.
- `rule`: the identity of the parser that read the file, such as `macos-document-v4`. `unsupported` tells that no format of the parser reads the file.
- `status`: `computed` (`content` holds the text), `empty` (the parser found no text, such as in a photo without words) or `failed` (`error` tells why).
- `content`: the text. It is NULL unless `status` is `computed`.
- `error`: why the read failed. It is NULL unless `status` is `failed`.

Readers join `attachmentRef` to `ref`:

```sql
SELECT a.id, t.content
FROM attachments a JOIN attachment_text t ON t.ref = a.attachmentRef
WHERE t.content LIKE '%invoice%';
```

The attachment text is a derived dataset of the import. No source reads it. `Connector.connection` declares it when the import stores files: elt-sqlite's `ComputedDataset` named `attachment_text`, over the tables of the streams that store files, with elt's `DocumentText` as its rule. The rule reads the `attachmentRef` column and asks the host's parser for the text. The data is in the table `raw_attachment_text`. When the declaration of that table changes, a refresh replaces the table, and the parser reads each file again.

The pipeline refreshes the dataset after each pass. Each refresh does these steps:

1. It deletes the row of each copy that no row of the import references.
2. It reads each copy that has no row, that has a row from a different parser identity, or that has a `failed` row.
3. It reads as many copies at one time as the Mac has CPUs. An image read that is more than the OCR workers of the host can do waits in their pool. The host sizes that pool from the CPUs and the free memory of the Mac.
4. It reads one file in each call, as many calls at once as the Mac has cores, and commits each file when its read ends. Readers see the text of a file as soon as it is read, and a slow file holds back no other file. A refresh that stops keeps the files that it committed.

The name of a stored copy comes from its bytes, in its field. Thus, the parser reads one file that is in three chats one time. When two streams store the same bytes, they make two copies, and the parser reads each copy.

A file that the parser cannot read gets a `failed` row with its error. This does not fail the import. The next refresh reads the file again, because Vision in a sandbox, a full disk or an `osascript` timeout fail only for some time. A different error, such as a folder that the refresh cannot open, fails the refresh. A copy that a commit removes during the refresh gets no row. When the identity of a format or a model changes, the parser reads again the copies of that format. When the parser stops reading a format, such as audio when transcription is off, a `computed` row of that format stays.

A one-shot import (the `sync` command of the CLI, the Sync button of the plugin) refreshes the text after the pass, also when some copies failed. Thus, a sync ends with the text of the files that it stored. `sync watch` refreshes in the background after each pass, one refresh at a time. When passes commit during a refresh, the watch does one more refresh after it. Thus, the next pass of the import does not wait for the parser. The failure of a refresh stops the watch. No host shows a refresh as a pass. A stored copy that the parser did not read yet has no row. Thus, the search results are complete only after the text is up to date with the sync.

`ConnectorHost.documentParser` is supplied by each host. The CLI and plugin compose it from the saved transcription choice. Each host builds the pool of OCR workers that reads images (`Pool` from `@zukhruf/pool` with the `LeaderFirst` startup and the `HillClimbing` sizing, which adds workers while they add throughput, up to what the Mac's CPUs and free memory afford); `Transcription` builds the pool of the chosen speech model's engine, which loads the weights as soon as the model is chosen. The plugin's server builds its OCR pool when it starts. The CLI builds its pools only for a sync or a watch, so `query`, `status` and help start no native process. Enabling or changing that choice processes audio from the selected imports; changing the audio model does not invalidate PDF, image or text extraction. Disabling transcription preserves existing successful transcripts. Failed files are retried on the next sync. A sync's attachment text is queryable in `attachment_text`, joined to the source view through `attachmentRef = ref`. elt's [document parsing reference](https://github.com/ezzabuzaid/elt/blob/main/docs/reference.md) describes `MacOSDocumentParser` and the local transcription model.
